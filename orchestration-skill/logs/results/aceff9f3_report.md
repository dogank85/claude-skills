# Error Message Audit - Detailed Report

**Date:** December 7, 2025
**Task ID:** aceff9f3
**Objective:** Review error messages in `packages/api/src/routers/*.ts` for user-friendliness, suggest alternatives, and check for sensitive information exposure.

## Methodology

1.  Identified all `.ts` files within `packages/api/src/routers/`.
2.  Filtered out test files (`.test.ts`, `.integration.test.ts`) to focus on core router logic.
3.  Manually reviewed each remaining router file, looking for `TRPCError` instances and other string literals that appeared to be user-facing error messages.
4.  Evaluated identified messages against criteria for user-friendliness, technical jargon, and potential exposure of internal/sensitive information.
5.  Compiled findings into this detailed report and a concise summary.

### 3. Other Files (`privacy.ts`, `credits.ts`, `consent.ts`, etc.)

Many error messages in these files follow similar patterns to those found in `auth.ts` and `story.ts` (e.g., `Parent profile not found.`, `Authentication required.`, `FORBIDDEN` or `UNAUTHORIZED` messages, various validation errors). The principles outlined above for improving user-friendliness and avoiding technical jargon apply uniformly across the codebase.

Some specific examples from `credits.ts` that were noted:

*   `APPLE_SHARED_SECRET is missing` / `GOOGLE_PLAY_SERVICE_ACCOUNT is missing`: These are internal configuration errors. User-facing message should be `Configuration error. Please contact support.`.
*   `Failed to verify receipt with Apple` / `Failed to verify purchase with Google`: These are good, but the `cause: error` should ideally not expose the raw error message to the client, especially if it contains details from the external service.

## General Recommendations

1.  **Centralize Error Messaging:** Consider creating a centralized error messaging utility or an `enum` for user-facing error messages to ensure consistency, prevent accidental exposure of technical details, and simplify internationalization in the future. This can map internal codes/statuses to appropriate user-friendly messages.
2.  **Avoid Technical Jargon:** Refrain from using terms that reference internal systems, database models (e.g., "Supabase", "Parent profile"), or specific infrastructure details in messages intended for end-users.
3.  **Graceful Handling of External API Errors:** When integrating with external APIs (e.g., Supabase, Apple, Google), always wrap their raw error messages in generic, user-friendly messages for the client. Log the full technical error on the server-side for debugging.
4.  **Actionable Feedback:** Where possible, error messages should not only state the problem but also suggest a clear next step for the user (e.g., "Please try again," "Contact support," "Request a new link").
5.  **Review `cause` field:** Ensure that the `cause` field of `TRPCError` is not inadvertently exposing sensitive internal error objects or messages directly to the client. The `cause` is primarily for server-side logging and debugging.
