# Delegation Patterns

This document describes the "Fire and Forget" pattern used by the Orchestration Skill to manage headless agents without context bloat.

## The Problem: Context Bloat

When an orchestrator runs a background process and listens to its output (stdout/stderr), every line of log generated by the worker agent is fed back into the orchestrator's context window. This rapidly consumes tokens, leading to:
1.  Increased costs.
2.  Loss of earlier context (forgetting the plan).
3.  Performance degradation.

## The Solution: Fire and Forget

The "Fire and Forget" pattern decouples the orchestrator from the worker's output stream.

### 1. Launching (Fire)

*   **Orchestrator**:
    1.  Runs `delegate_task.py`.
    2.  Receives a `TASK_ID`.
    3.  Does **NOT** wait.
*   **Worker Agent**:
    1.  Runs in background.
    2.  Writes logs to `logs/raw/<TASK_ID>.log`.
    3.  Writes summary to `logs/results/<TASK_ID>.summary.md`.
    4.  Updates status in `logs/status/<TASK_ID>.status.json`.
*   **Orchestrator**:
    1.  Periodically runs `check_status.py --task_id <TASK_ID>`.
    2.  Reads `logs/results/<TASK_ID>.summary.md` ONLY when status is "COMPLETED".

### 2. Monitoring (Forget)

The orchestrator does *not* poll the log file. It only checks the status file.
*   **Mechanism**: The worker wrapper script writes to `logs/<id>.status.json` on start and exit.
*   **Check**: The orchestrator calls `check_status.py` which reads this small JSON file.

### 3. Completion

When the worker finishes, it writes a summary to `logs/<id>.summary.md`.
*   **Mechanism**: The prompt includes instructions for the agent to generate this specific file.
*   **Retrieval**: The orchestrator reads *only* this summary file to understand the result.

## Session Resumption

To preserve context between tasks without bloating the orchestrator, we use **Session Resumption**.

1.  **Capture**: When a task completes, the `delegate_task.py` script extracts the agent's `session_id` from the JSON output and saves it to the `status.json` file.
2.  **Resume**: When starting a new task, you can pass `--parent_task_id <ID>`.
3.  **Mechanism**: The script reads the `session_id` from the parent's status file and passes it to the agent (e.g., `claude --resume <SESSION_ID>`).

**Benefits:**
*   **Orchestrator**: Only stores the `task_id` (tiny).
*   **Worker Agent**: Remembers the entire conversation history.
*   **Cost**: You don't pay to re-send the context to the orchestrator or the worker.

## Reasoning Effort

For complex tasks (debugging race conditions, architectural refactoring), you can boost the agent's capabilities:

*   **Flag**: `--effort high` (Default: `standard`)
*   **Mechanism**:
    *   **Gemini**: Switches from `flash` to `gemini-3-pro-preview`.
    *   **Claude**: Switches from `haiku` to `sonnet`.
    *   **Codex**: Enables `model_reasoning_effort="high"` (e.g. o1/o3 behavior).

**Usage:**
```bash
python3 scripts/delegate_task.py --agent gemini --prompt "Debug complex deadlock" --effort high
```

## Sandboxing

For security, especially when delegates are executing code or shell commands, you should enable sandboxing.

*   **Flag**: `--sandbox`
*   **Mechanism**:
    *   **Claude**: Uses `--sandbox` (OS-level isolation).
    *   **Gemini**: Uses `--sandbox` (Seatbelt/Container).
    *   **Codex**: Uses `--sandbox workspace-write` (Allows writing to project, blocks system access).

**Usage:**
```bash
python3 scripts/delegate_task.py --agent codex --prompt "Install dependencies" --sandbox
```

## Detailed Reporting

Sometimes you need more than a concise summary. Use the `--report` flag to instruct the agent to write a detailed report to `logs/results/<task_id>_report.md`.

*   **Flag**: `--report`
*   **Output**: `logs/results/<task_id>_report.md`

**Usage:**
```bash
python3 scripts/delegate_task.py --agent claude --prompt "Analyze database performance" --report
```

## Best Practices

*   **Trust the System**: Do not try to `tail` the log file unless debugging a failure.
*   **Clear Instructions**: Ensure the prompt explicitly tells the agent what to put in the summary file.
*   **Idempotency**: If possible, design tasks so they can be retried if they fail.
*   **File Containment**: NEVER instruct an agent to write reports to the project root. All outputs must go to `logs/results/`.

## Agent Selection Criteria

When deciding which agent to delegate a task to, use the following criteria:

### Choose Claude Code when:
- Workflow requires complex tool orchestration
- Need to programmatically read/write files (reliably)
- Workflow has multi-step tool execution
- Comprehensive validation or analysis is needed

### Choose Gemini CLI when:
- Workflow is a blend of analysis and execution
- Need shell command context injection
- Workflow benefits from `@{file}` injection
- Performing technical analysis and review tasks (`--yolo` mode is great for non-destructive reviews)

### Choose Codex CLI when:
- Workflow is pure execution (running tests, running commands)
- Need fast, keyboard-first execution
- Instructions-only approach works
- Straightforward implementation tasks
